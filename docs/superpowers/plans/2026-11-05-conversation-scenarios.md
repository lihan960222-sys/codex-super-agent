# 手机自然对话验收场景：120 项基准

状态：设计，所有用例均为未执行。与同目录 `2026-11-05-conversation-validation.md` 配套。每行是独立故事，不是仅匹配一句话；箭头表示连续发消息，不应重置上下文。输入引用的任务均为合成数据。

## 公共夹具与判定

固定逻辑别名，实际 ID 在每次运行生成：A=激光焊接铝板参数；B=激光焊接钢板报告；C=SolidWorks 支架图纸；D=AI 资料整理。A/B 同职责、不同任务和 thread。各行明确需要的状态由夹具初始化，不推断前一行结果。所有未选任务状态、设置和文件哈希保持不变。

消息绑定通过测试发送通道返回的真实测试 message_id 建立，不伪造不存在的送达记录。至少加入两项相似标题、一个已停止任务、一个已完成任务、一个待澄清问题作为干扰项。场景要求只有一个候选时显式替换夹具。

层级：**N**=真实 Router 语义/表达＋真实本地状态逻辑；**E**=真实 Router＋真实 Worker 执行并查原生产物；**F**=故障注入/确定性程序检查（涉及语言时叠加 N）。模拟 Telegram 标为 simulated，永不标为真实手机传输。N 层可控 Worker 替身仅证明调度或控制，不证明实际执行。所有宣称干活成功的验收必须有 E 层佐证。

`K` 为关键重复组，每轮独立运行 3 次：C01–C03、D01–D03、E01–E03、F01–F03、G01–G03、H01–H03、N01–N03、P01–P03，共 24 项。其他基准每轮至少一次。不得挑选最好一次覆盖失败。

## 故事串联（每轮都要跑，不用孤立用例代替）

1. **原故障自然复演**：建 A/B→全停→建 C/D→问状态→“都开始”→“前者”→取消 A→“不就这一个么”→状态→重启。不得由脚本偷偷加全名来救场；若需要用户答复，只按已固定的故事脚本回答。
2. **两项目穿插**：A 执行→补条件→D 新任务→回复 A 旧消息→B 新任务→“钢板不要了”→汇报 A→发 A 文件。验证三个 thread 和所有未选状态。
3. **隔天回来**：多轮/轮换→新建测试协调器→不提供旧 Telegram reply→自然描述目标→进度回顾→续作→完成产物。时间跨度使用测试记录时间模拟，不谎称真的等待一天。
4. **故障中控制**：Worker 请求已接收→响应丢失→主人取消→协调器恢复→迟到报告→恢复另一个任务。对账和人的最新意图优先。
5. **多模态完整回路**：语音指派→图片补充→文件输入→Worker 实际读写→Router 交付文件→回复文件续问→取消。每项媒体单列实际能力与缺口。

这些串联必须生成独立 run/case 记录；成功不靠在步骤间手动修数据库。夹具只允许在每个故事开始时建立前置状态。

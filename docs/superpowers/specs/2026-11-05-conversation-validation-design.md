# 手机对话全链路测试设计

日期：2026-11-05。状态：测试设计，尚未执行本次三轮验证。基线：`dcef829` / v0.1.1。

## 目的与约定

用户从 Telegram 一个私聊窗口自然指派、追问、暂停、取消和恢复任务，不需要记 task ID、worker ID 或原生会话 ID。成功必须同时满足“理解了哪个任务、真正改变了状态或执行了工作、回复符合证据”。措辞自然但没有派活不能算成功；拒绝错误操作但一直无法完成正确操作，也不能算成功。

用户指定流程：先编写测试流程；实施时每轮先完整测试，收齐问题后集中修改，再进入下一轮，共三轮。本次只交付文档，不改运行代码、不执行三轮、不部署。

## 当前证据与不足

- CHANGELOG 记录上一版 200 项自动化检查通过。本次只核对记录与源码，没有重新运行，也不能将其当成本轮结果。
- `control-dialogue.test.mjs` 等覆盖了状态机，但不少测试直接构造正确的 Router 动作；`system.test.mjs` 的 FakeRPC 也直接返回固定动作。因此它们不能证明真实模型理解手机端自然语言。
- `probe-cancel.mjs` 使用真实 Router 模型、独立账本和模拟 Telegram，只有三个取消/确认案例。部分路径由脚本补充完整任务名，并预先构造结构化问题。这不足以覆盖自然歧义的产生与解决，也没有真实 Worker 执行。
- 当前语义层存在短卡片、近期消息、检索次数和轮换预算；必须验证信息被截断之后的寻址，而不只验证少量任务。
- 静态阅读发现单项 stop 与全局 pause 在实现中语义不同；独立“暂停某任务”的完整语义需实测。此处是风险假设，不冒充已经复现的缺陷。

## 路径选择

1. 只扩展现有单元测试：快，但继续绕过模型理解，无法回答用户关切。
2. 全部经真实 Telegram 私聊测：最接近手机，但自动模拟用户需要另一个授权入口，容易影响正式接单，且难控制故障与复现。
3. **采用：复用现有 Node 测试 + 真实模型的隔离全链路回放 + 明确标注的线上传输验证。** 回放从 Telegram update 形状的输入进入现有 Runtime，真实 Router 决策和表达；用真实 Worker 执行有限本地文件任务，其他高风险动作使用可观测替身。

第 3 项为执行者依据现有代码选择的方案，不声称用户已审阅。没有 Telegram 用户侧自动化入口时，不能把注入 update 说成真正手机端端到端测试，不能为了测试另开消费者抢正式 Bot 的 getUpdates。

## 必须守住的行为

- 每个输入有明确的归属、澄清、回答或拒绝结果；不会悄悄丢弃，也不能用“收到”代替执行。
- 同一职责可有多个独立任务会话；旧任务追问回旧会话，新任务不污染旧上下文；跨任务资料共享须按限定证据发生。
- 明确回复绑定优先，但引用旧消息中提出的全新任务不能被盲目当成旧任务续问；存在冲突要解析或澄清。
- 单项暂停不等于取消；取消保留记录但不自动复活。全局暂停与单项状态分别验证。不会把已完成任务改成已取消。
- 队列、资源等待、等待用户、执行中和执行失败分别说明；有实际原生启动证据才能说“开始工作”。
- Worker 结果经 Router 交付；保留必要事实、问题、证据及文件关联，不转发原始 Worker 文风、不虚构产物。
- 后台断连、重启、旧回调和重复输入不会引起重复执行或复活人工停止任务。
- 明确绑定的普通追问跳过模型分流；交付的 Router 调用单独计数。不得为了稳定性把所有历史全文塞回 Router。
- 输入媒体、设置、权限、称号、长期知识、主动工作都纳入场景；未支持能力如实报告，已承诺能力缺失计缺陷，不能改标“不支持”消除失败。

## 隔离与可追溯

使用本机 Windows、现有 Node 24 和已登录的 Codex App Server。测试目录在仓库已忽略的 `local/conversation-validation/<runId>/`；产物可置于 `E:\codex_bot\_验收\<runId>`，必须显式传入 outputRoot 并核验路径。使用合成任务和媒体，不复制私人聊天、个人偏好或生产账本到公开仓库。

按用户指定，三轮测试及最终验收固定使用 Router：`gpt-6-luna / medium`，Worker：`gpt-6.1-sol / medium`，写入测试设置副本；不改生产设置、不删除生产原生会话。模型不可用时记录阻塞，不自动替换。L 组模型切换用例只在自己的隔离夹具中临时改变设置，记录实际请求值，结束后恢复基线。真实 Worker 测试只允许在专用目录创建/修改/读取验收文件；模拟桌面互斥，不操作正在使用的 SolidWorks。模型调用消耗实际账户额度，逐项记录用量，取不到则填 unknown。

故障只注入测试适配器或独立测试进程，不停止共享 App Server、正式 Bot、正式 Watchdog，不切断整机网络。执行前验证测试目录、配置和输出路径没有指向生产数据。

每轮保存基线提交、用例版本、模型/强度、参数、事件及工具调用、前后状态、原生 thread/turn、文件哈希、脱敏对话、故障原因与修复提交。公开仅提交合成用例、测试代码、脱敏总结和变更记录。

## 三轮边界与验收

每轮运行全部 120 个基准场景、固定的高风险重复组，以及该轮新增压力场景。故障发现后继续独立用例，禁止边测边改产品代码；因服务不可用无法执行的项标记 blocked，并补测，不能算通过。完整结果保存后才定位、集中修复和验证。第三轮修复后仍须最终全量回归，不得拿修复前结果验收。

错误对象变更、越界文件修改、未经授权复活、伪报执行/完成、串会话均为发布阻断。所有必需场景及最终回归通过才能宣布本范围验收成功；合理澄清是成功的一部分，无意义的反复澄清是失败。限定重复次数不构成永不出错的保证。
